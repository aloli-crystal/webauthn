= aloli-crystal/webauthn
:toc: left
:toc-title: Sommaire

Bibliothèque WebAuthn (W3C niveau 3) côté partie de confiance pour Crystal : passkeys, décodage CBOR et COSE, vérification ES256 et RS256.

== Pourquoi

Une passkey ne laisse **aucun secret partagé sur le serveur**. La clé privée
est détenue par l'appareil de l'utilisateur — Trousseau macOS, Windows Hello,
TPM, clé de sécurité — et déverrouillée par l'appareil lui-même, par
biométrie ou par le mot de passe de session. Le serveur ne stocke qu'une clé
publique : une fuite de la table des identifiants ne donne rien de
réutilisable. Et comme la signature est liée à l'origine pour laquelle elle a
été produite, elle ne peut pas être rejouée contre un site d'hameçonnage.

Un authentificateur exigeant la vérification de l'utilisateur est donc *déjà
multifacteur en un seul geste* : possession de l'appareil, plus ce qui le
déverrouille. Y empiler un code à usage unique n'ajoute rien.

Ce shard implémente la **partie de confiance** — le côté serveur. Il ne parle
pas aux authentificateurs, c'est le navigateur qui s'en charge. Il vérifie ce
qui revient.

== Ce qui fonctionne aujourd'hui

En cours. Ce qui est implémenté et couvert par des specs :

[cols="1,3",options="header"]
|===
|Composant |État

|`WebAuthn::CBOR`
|Décodeur du sous-ensemble CBOR utilisé par WebAuthn (RFC 8949). Strict par
conception : il analyse des entrées atteignables par un attaquant, donc les
longueurs indéfinies, les tags, les flottants, les clés de map en double, les
longueurs déclarées excessives et les imbrications profondes sont refusés
plutôt que tolérés.

|`WebAuthn::COSE`
|Décodage des COSE_Key (RFC 8152) pour EC2 et RSA, projetées sur les clés de
https://github.com/aloli-crystal/jose[jose], avec vérification de signature.
Un algorithme que la partie de confiance n'a pas proposé est refusé : un
appelant ne peut pas forcer une négociation à la baisse.

|`WebAuthn::AuthenticatorData`
|Le bloc binaire que signe l'authentificateur (§6.1), y compris les données
d'identifiant attestées et leur clé COSE de longueur variable.

|`WebAuthn::ClientData`
|Ce dont le navigateur se porte garant (§5.8.1) : type de cérémonie, défi et
origine.

|Cérémonie d'enregistrement
|`RelyingParty#verify_registration` (§7.1). Attestation `none` uniquement.

|Cérémonie d'authentification
|`RelyingParty#verify_authentication` (§7.2), contrôle du compteur de
signature compris.
|===

Les algorithmes proposés par défaut sont **ES256 et RS256**. ES256 couvre les
authentificateurs de plate-forme Apple et Android ainsi que la plupart des
clés de sécurité ; RS256 couvre Windows Hello, qui s'enrôle couramment avec.
N'en proposer qu'un exclut toute une population d'utilisateurs.

Hors périmètre pour l'instant : la vérification des attestations au-delà de
`none`. Ce shard ne cherche pas à prouver la marque et le modèle de
l'authentificateur, ce dont une partie de confiance a rarement réellement
besoin, et qui a des conséquences sur la vie privée.

== Installation

[source,yaml]
----
dependencies:
  webauthn:
    github: aloli-crystal/webauthn
    version: "~> 0.1"
----

== Démarrage rapide

[source,crystal]
----
require "webauthn"

# Le RP ID est en pratique définitif : le changer invalide toutes les
# passkeys déjà enrôlées. Le fixer au suffixe de domaine enregistrable
# partagé par toutes les instances qui doivent accepter la même clé.
rp = WebAuthn::RelyingParty.new(
  id: "noalyss.example",
  origins: ["https://client1.noalyss.example"]
)

# --- Enregistrement ---------------------------------------------------
challenge = WebAuthn.generate_challenge   # à stocker côté serveur, usage unique

credential = rp.verify_registration(
  attestation_object: params["attestationObject"],
  client_data_json: params["clientDataJSON"],
  challenge: challenge
)
# Persister credential.id, sa clé publique et credential.sign_count.

# --- Authentification -------------------------------------------------
challenge = WebAuthn.generate_challenge

assertion = rp.verify_authentication(
  credential: stored_credential,
  authenticator_data: params["authenticatorData"],
  client_data_json: params["clientDataJSON"],
  signature: params["signature"],
  challenge: challenge
)
# Persister assertion.sign_count — sans quoi le contrôle de clonage ne sert
# plus à rien.
----

Les deux cérémonies lèvent `WebAuthn::VerificationError` au lieu de renvoyer
un booléen : un appelant ne peut pas oublier de vérifier le résultat. Un
clonage suspecté lève `WebAuthn::ClonedAuthenticatorError`, qu'il vaut la
peine de distinguer : la signature *était* valide, ce n'est donc pas une
falsification — l'identifiant existe en deux exemplaires, et l'utilisateur
doit en être informé.

La vérification de l'utilisateur est exigée par défaut. C'est elle qui rend
une passkey multifacteur à elle seule ; passer `user_verification:` pour
l'assouplir.

== Conventions ALOLI

Ce shard suit les conventions de l'écosystème
https://github.com/aloli-crystal[aloli-crystal/*] :

* Constante `VERSION` lue au compile-time depuis `shard.yml` —
  pas de désynchro possible.
* CLI : `webauthn help [<sub>]` (équivalent UX standard de
  `--help` + focus par sous-commande).
* Branche par défaut `production` (pas `main`).
* Versioning SemVer 3-chiffres pour création, 4-chiffres pour
  portage de gem Ruby.

Pour démarrer un nouveau shard avec ces conventions :
https://github.com/aloli-crystal/shard-template[aloli-crystal/shard-template].
